1 · Where the project started

Before any DevOps work, YatruSathi was three unrelated codebases, each deployed by hand to a different free host:

ServiceHow it ranArtefacts left behind
Django backendPushed to Render; Render ran scripts/build.sh then scripts/start.shrender.yaml, Procfile, runtime.txt, scripts/*.sh
React frontendA GitHub Action built it and pushed dist/ to Cloudflare Pages-yatruSathiFrontend-/.github/workflows/deploy.yml
Flask chatbotRun manually with python app.py — no deployment at allnone

Problems this created

  • No reproducibility — "works on my machine"; Python/Node versions and system packages differed per developer and per host.
  • Three pipelines, three dashboards — a change spanning frontend + backend could not be tested or shipped together.
  • Secrets in the code — an OpenAI key, Supabase keys, a Postgres password (YatruSathi@123 / Minorproject@123) and a Gmail app password were committed and pushed to public repos (see scripts/deploy_setup.sh, which still prints them).
  • Data model unclear — backend had drifted from Supabase Postgres to a local SQLite file; Render's disk is wiped on every deploy, so data did not survive.
  • The chatbot was invisible to CI, to ops, to everyone.

Two large planning documents (AUDIT_REPORT.md, REFACTORING_QUICK_START.md) were written to catalogue this and were later removed once the work they described was done.

3 · Monorepo consolidation

The three apps live in one repository at:

DirectoryServiceStack
-yatrubackend-/REST API & data modelDjango 6, DRF, SQLite→Postgres
-yatruSathiFrontend-/Web clientReact 19, TypeScript, Vite 7, MUI 6
-Yatrusathi-AIchatbot/AI assistant & realtime chatFlask, Flask-SocketIO, Groq

(The odd leading/trailing dashes are the original repo names, kept so history and external links still resolve.)

The submodule → vendor fix (commit 90ae7f6)

The first commits added the three directories as git submodule pointers — a submodule stores only a commit hash, not the files, and needs a .gitmodules file plus a recursive checkout to populate. There was no .gitmodules, so:

git clone …              → three EMPTY directories
CI: working-directory: ./-yatrubackend-  → "no such file" → every job fails

Commit 90ae7f6 deleted the gitlinks and committed the actual file trees ("vendoring"). From then on a plain git clone or CI checkout has everything.

Why one repo, not three. A single pipeline can build, test and release all three services from one commit; a change that touches the API and the client is one reviewable pull request; there is one place for docker-compose.yml, one CI config, one Terraform root. The cost — everyone clones all three services — is negligible at this size.

4 · Environment-variable strategy

Rule: nothing is hard-coded; every deployment-specific value comes from an environment variable; no real secret is ever committed. Established in commit e5543be and documented in docs/environment.md.

The four .env.example files

FileCommitted?Purpose
.env.exampleyesRoot — values docker-compose.yml interpolates (ports, image tag) plus per-service overrides.
-yatrubackend-/.env.exampleyesEvery key Django reads: SECRET_KEY, DEBUG, ALLOWED_HOSTS, CORS/CSRF, admin account, e-mail.
-yatruSathiFrontend-/.env.exampleyesThe VITE_* build-time values (API URL, chatbot URL, Supabase).
-Yatrusathi-AIchatbot/.env.exampleyesSECRET_KEY, GROQ_API_KEY, GROQ_MODEL, optional Supabase.
<each>/.envno — git-ignoredThe real local values. Copied from .env.example.

Each app already loads its own file: Django and Flask via python-dotenv (load_dotenv()), the frontend via Vite (import.meta.env.VITE_*, frozen in at build time).

Why .env.example is committed but .env is not. The example is the contract — the canonical list of every variable the service understands, with safe placeholder values, so a new developer knows exactly what to set. The real .env holds actual secrets and is git-ignored. This pattern is repeated at every layer: Terraform has terraform.tfvars.example, the deploy has GitHub repository variables.

.gitignore — the secret-safety net

# ── Secrets / environment ──

# ── Terraform (added Sep 7) ──

The !*.tfvars.example / !.env.example lines are re-includes — ignore the whole class, keep the one template. The Terraform lock file .terraform.lock.hcl is committed (it pins provider checksums for reproducible installs).

docs/environment.md

A reference table of every variable each service reads — required vs optional, default, and notes — plus a "rotate before production" list of the credentials that had been committed. That list is now actioned by docs/secret-rotation.md and enforced by the gitleaks CI job (§8).

5 · Containerisation — the three Dockerfiles

A container image is a frozen, self-contained filesystem with the app and exactly the runtime it needs. The identical image runs on a laptop, in CI, and in the cloud. All three share two patterns:

  • Multi-stage build — a "builder" stage installs dependencies; a slim "runtime" stage copies only the result. Build tools never ship.
  • Non-root user — the process runs as an unprivileged app user.

The backend and frontend Dockerfiles pre-existed (entered the repo with the vendoring in 90ae7f6); the chatbot one and its support files were written in 732127c.

5.1 · Backend — -yatrubackend-/Dockerfile

FROM python:3.13-slim-bookworm AS builder
ENV PIP_NO_CACHE_DIR=1  PIP_DISABLE_PIP_VERSION_CHECK=1
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
WORKDIR /app
COPY requirements.txt .
COPY requirements/ requirements/
RUN pip install --upgrade pip && pip install -r requirements.txt

FROM python:3.13-slim-bookworm AS runtime
ENV PYTHONDONTWRITEBYTECODE=1  PYTHONUNBUFFERED=1  PIP_NO_CACHE_DIR=1 \
    DJANGO_SETTINGS_MODULE=backend.settings  PATH="/opt/venv/bin:$PATH"
RUN groupadd --system app && useradd --system --gid app --home-dir /app app
WORKDIR /app
COPY --from=builder /opt/venv /opt/venv
COPY . .
RUN chmod +x docker-entrypoint.sh scripts/*.sh \
 && mkdir -p data media logs staticfiles \
 && SECRET_KEY=build-only DEBUG=False python manage.py collectstatic --no-input \
 && chown -R app:app /app
USER app
EXPOSE 8000
HEALTHCHECK … CMD python -c "… GET /api/ … status < 500 …"
ENTRYPOINT ["./docker-entrypoint.sh"]
LineWhat & why
FROM python:3.13-slim-bookworm AS builderOfficial Python 3.13, the "slim" Debian variant (no compilers/docs). Named so the runtime stage can copy from it.
RUN python -m venv /opt/venv + ENV PATHAn isolated, portable virtual-environment. Putting its bin first on PATH makes every later pip/python use it.
COPY requirements*.txt before COPY . .Docker layer caching: the slow pip install layer is reused for every build where requirements are unchanged, even when app code changes.
PYTHONDONTWRITEBYTECODE / PYTHONUNBUFFEREDNo .pyc files; flush logs immediately.
groupadd … useradd … app + later USER appNothing runs as root after this point.
COPY --from=builder /opt/venv /opt/venvBring the finished dependencies without pip/build machinery.
collectstatic … SECRET_KEY=build-onlyBake Django's admin CSS/JS into the image at build time (throw-away key just to let settings import), instead of gathering them on every start.
mkdir -p data media logs staticfiles + chownPre-create the volume mount-points owned by app, so a fresh Docker volume comes up writable, not root-owned.
HEALTHCHECK … status < 500Container is "healthy" if Django answers anything below 500. Inline Python because the slim image has no curl/wget. A forwarded-proto header stops the HTTPS-redirect turning it into a loop.
ENTRYPOINT ["./docker-entrypoint.sh"]The container runs a start-up script, not the server directly.

-yatrubackend-/docker-entrypoint.sh

set -euo pipefail                                # abort on any error / unset var / failed pipe
python manage.py migrate --no-input             # apply DB schema changes
python scripts/seed_db.py || echo "…continuing" # optional sample data, non-fatal
exec gunicorn backend.wsgi:application \
    --bind "0.0.0.0:${PORT:-8000}" \
    --workers "${WEB_CONCURRENCY:-3}" \
    --timeout "${WEB_TIMEOUT:-120}" \
    --access-logfile - --error-logfile -

Migrations run first so the schema is always current before traffic. Gunicorn is the production server (never Flask/Django dev servers in production); exec makes it PID 1 so it receives stop signals. 3 sync workers by default (the backend has no long-lived connections).

5.2 · Frontend — -yatruSathiFrontend-/Dockerfile

Pre-existing; this work added the two VITE_SENTRY_* build arguments.

FROM node:22-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci                              # install EXACTLY the locked tree
ARG VITE_API_BASE_URL
ARG VITE_CHATBOT_URL
ARG VITE_SUPABASE_URL
ARG VITE_SUPABASE_ANON_KEY
ARG VITE_SENTRY_DSN              # ← added
ARG VITE_SENTRY_ENVIRONMENT     # ← added
ENV VITE_API_BASE_URL=$VITE_API_BASE_URL … VITE_SENTRY_DSN=$VITE_SENTRY_DSN …
COPY . .
RUN npm run build                       # → static files in /app/dist

FROM nginx:1.27-alpine AS serve
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
HEALTHCHECK … wget -q -O /dev/null http://127.0.0.1/ …
Why the frontend needs build arguments, not runtime environment variables. Vite replaces every import.meta.env.VITE_* with a literal string when the bundle compiles. By the time nginx serves the files there is no process to read env vars — the values are frozen into the JavaScript. So the API URL, chatbot URL and Sentry DSN must be given at docker build time. This is exactly why the deploy script (§12) rebuilds the frontend image per environment.

-yatruSathiFrontend-/nginx.conf

  • location / → try_files $uri $uri/ /index.html — unknown paths return the app shell so React Router handles them (this is what makes a SPA survive a refresh / deep link).
  • location /assets/ → Cache-Control … immutable, one year — build assets have content-hashed names.
  • location = /index.html → no-cache — a new deploy is picked up immediately.
  • gzip on text types; security headers (X-Content-Type-Options, X-Frame-Options, Referrer-Policy) on every response.

5.3 · Chatbot — -Yatrusathi-AIchatbot/Dockerfile (new)

FROM python:3.13-slim-bookworm AS builder
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY requirements.txt .
RUN pip install --upgrade pip && pip install -r requirements.txt

FROM python:3.13-slim-bookworm AS runtime
ENV … PATH="/opt/venv/bin:$PATH"  GUNICORN_THREADS=50
RUN groupadd --system app && useradd --system --gid app --home-dir /app app
COPY --from=builder /opt/venv /opt/venv
COPY . .
RUN chown -R app:app /app
USER app
EXPOSE 5005
HEALTHCHECK … CMD python -c "… GET /health … status < 400 …"
CMD ["sh","-c","exec gunicorn app:app --bind 0.0.0.0:5005 \
    --worker-class gthread --workers 1 --threads ${GUNICORN_THREADS:-50} \
    --timeout ${GUNICORN_TIMEOUT:-120} --access-logfile - --error-logfile -"]
Why --workers 1. The chatbot uses Flask-SocketIO in threading mode, which keeps every chat room and each user's conversation history in one process's memory. A second worker would have separate memory, so users would randomly get amnesiac replies. One worker with many threads gives concurrency without splitting that state. Scaling past one process needs Redis — §9.4 and §11.6.
Why gthread. Gunicorn's default "sync" worker serves one request at a time and drops idle connections — fatal for Socket.IO / Server-Sent-Events streams. gthread holds long-lived connections open.

Support files (new)

  • requirements.txt — pinned versions (Flask==3.1.3, Flask-SocketIO==5.6.1, groq, gunicorn, plus sentry-sdk and redis added in §9). Before this the service was installed with an ad-hoc pip install flask … that could resolve to different versions per day.
  • .dockerignore — keeps .git, .env, venv/, caches out of the build context and image.
  • .flake8 — the bundled knowledge_base.py is a huge data-style file; CI hard-fails only on real defects and reports the rest.

The backend and frontend also carry pre-existing .dockerignore files with the same intent (exclude VCS, secrets, local data, docs; the backend one also excludes render.yaml/Procfile so those legacy files don't reach the image).

6 · Local orchestration — docker-compose.yml

One command — docker compose up --build — starts the whole stack: three services, a private network so they resolve each other by name, and named volumes so data survives a restart. First added in b5dae18 (backend + frontend); the entire chatbot service and the SENTRY_*/REDIS_URL wiring were added later.

Anatomy of a service

backend:
  build: { context: ./-yatrubackend- }         # build the image from that folder
  image: yatrusathi-backend:${IMAGE_TAG:-local}
  restart: unless-stopped                        # auto-restart on crash
  environment:
    SECRET_KEY: ${DJANGO_SECRET_KEY:-django-insecure-…}
    DEBUG: ${DJANGO_DEBUG:-True}
    SQLITE_PATH: /app/data/db.sqlite3
    SENTRY_DSN: ${SENTRY_DSN_BACKEND:-}          # blank ⇒ disabled
    SENTRY_ENVIRONMENT: ${SENTRY_ENVIRONMENT:-development}
    …
  ports: ["${BACKEND_PORT:-8000}:8000"]
  volumes:
    - backend_data:/app/data       # the SQLite file
    - backend_media:/app/media      # user uploads
  networks: [yatrusathi]
  healthcheck: { test: [python -c "… /api/ …"], interval: 30s, retries: 3 }
PatternMeaning
${VAR:-default}Use VAR; if unset or empty, use default. This is why the stack runs with no .env file at all.
ports: ["8000:8000"]host:container. Left = reachable from your machine; right = inside the container.
volumes: [name:/path]A Docker-managed disk. Survives down; only down -v deletes it.
networks: [yatrusathi]All three join one bridge network — backend can reach chatbot by that hostname.
healthcheckCompose tracks healthy/unhealthy; other services can wait for "healthy".

The frontend service — depends_on with health gates

frontend:
  build:
    context: ./-yatruSathiFrontend-
    args:
      VITE_API_BASE_URL: ${VITE_API_BASE_URL:-http://localhost:${BACKEND_PORT:-8000}/api/}
      VITE_CHATBOT_URL:  ${VITE_CHATBOT_URL:-http://localhost:${CHATBOT_PORT:-5005}}
      VITE_SENTRY_DSN:   ${VITE_SENTRY_DSN:-}
  ports: ["${FRONTEND_PORT:-8080}:80"]
  depends_on:
    backend:  { condition: service_healthy }
    chatbot:  { condition: service_healthy }
Why the frontend build args say localhost, not backend. These URLs are used by the visitor's browser, which is outside Docker and cannot resolve the compose hostname backend — only the port published on the host. Container-to-container calls use the compose name; the browser cannot.

Bottom of the file: networks: { yatrusathi: { driver: bridge } } and volumes: { backend_data:, backend_media: } — declare the shared network and the two persistent disks.

7 · The CI pipeline and how it evolved

CI = every push is automatically built, tested and scanned. GitHub Actions runs it; each job is an isolated Linux VM. The file is .github/workflows/ci.yml.

7.1 · Version 1 (commit b5dae18) — three jobs

on: { push:, pull_request:, workflow_dispatch: }
permissions: { contents: read }           # least privilege — read the repo, nothing else
jobs:
  frontend:  checkout → setup-node → npm ci → lint → typecheck → test → build
  backend:   checkout → setup-python → pip install → manage.py check
             → makemigrations --check → flake8 → pytest
  docker:    needs: [frontend, backend]
             checkout → docker compose build     # build both images, push nothing

Then commit da1d5ec bumped the action versions (checkout v4→v5, setup-node v4→v5, setup-python v5→v6) and Node 20→22 to match the Dockerfiles.

7.2 · The security job (commit 483abf4)

The docker job was renamed security and given Trivy scanning:

security:
  needs: [frontend, backend]     (later: + chatbot)
  env: { TRIVY_DB_REPOSITORY: public.ecr.aws/aquasecurity/trivy-db:2 }
  steps:
    - Trivy — dependency scan   (scan-type: fs, exit-code "0")   # REPORT only
    - docker compose build --pull                                 # build all images
    - Trivy — backend image    (exit-code "1", ignore-unfixed)   # FAIL on fixable HIGH/CRITICAL
    - Trivy — frontend image   (exit-code "1")
    - Trivy — chatbot image    (exit-code "1")   (added later)
SettingMeaning
dependency scan exit-code "0"Never fails the build — dependency CVEs are Dependabot's job.
image scans exit-code "1" + ignore-unfixed: trueFails the build on a HIGH/CRITICAL that has a fix available. Unfixable ones are ignored (nothing to do).
TRIVY_DB_REPOSITORY: public.ecr.aws/…Pull Trivy's CVE database from AWS's mirror to dodge Docker Hub rate limits.
if: ${{ !cancelled() }} on later scansScan the frontend/chatbot even if the backend scan already failed — see every problem in one run.

push-ecr job — publish images

needs: [security]
if: github.ref == 'refs/heads/main' && (push || workflow_dispatch)
permissions: { contents: read, id-token: write }   # id-token: request an OIDC token
steps:
  - docker compose build
  - aws-actions/configure-aws-credentials@v4  with role-to-assume: ${{ vars.AWS_DEPLOY_ROLE_ARN }}
  - aws-actions/amazon-ecr-login@v2
  - for svc in frontend backend chatbot:
      docker tag  yatrusathi-$svc:local  $REGISTRY/yatru-sathi-$svc:$SHA
      docker tag  …                       $REGISTRY/yatru-sathi-$svc:latest
      docker push both
Why OIDC, not an access key. GitHub mints a short-lived, signed token proving "workflow X, repo Y, branch main". AWS trusts that token and returns temporary credentials (~1 hour). There is no long-lived AWS_ACCESS_KEY_ID stored in GitHub to leak, and the trust is scoped to exactly this repo + branch.
Why tag with the commit SHA. :latest moves; :<sha> is immutable, so a rollback can point at the exact image a given commit produced.

8 · Dependabot, CodeQL, secret & Dockerfile scanning

8.1 · Dependabot

Initially enabled in the GitHub UI (it opened PR #1 — b098ff3 — bumping 7 backend pip packages). Now committed as .github/dependabot.yml covering five ecosystems:

version: 2
updates:
  - { package-ecosystem: pip,   directory: /-yatrubackend-/requirements, groups: {backend-python: {patterns: ["*"]}} }
  - { package-ecosystem: pip,   directory: /-Yatrusathi-AIchatbot,       groups: {chatbot-python: {patterns: ["*"]}} }
  - { package-ecosystem: npm,   directory: /-yatruSathiFrontend-,
      groups: {frontend-npm: {patterns: ["*"], update-types: ["minor","patch"]}} }
  - { package-ecosystem: github-actions, directory: / }
  - { package-ecosystem: docker, directories: [/-yatrubackend-, /-yatruSathiFrontend-, /-Yatrusathi-AIchatbot] }

groups bundles routine updates into one PR per ecosystem per week. The npm group is capped at minor/patch so a major React bump arrives as its own reviewable PR.

8.2 · .github/workflows/codeql.yml (added)

on: { push: {branches:[main]}, pull_request: {branches:[main]}, schedule: [{cron: "27 3 * * 1"}] }
jobs:
  analyze:
    permissions: { contents: read, security-events: write }
    strategy: { matrix: { language: [python, javascript-typescript] } }
    steps: init (queries: security-and-quality) → autobuild → analyze

CodeQL is GitHub's deep static-analysis engine: it builds a queryable database of the code and runs security queries (injection, path traversal, unsafe deserialisation, hard-coded credentials…). Findings land in Security → Code scanning. The weekly schedule re-scans with new queries even when nobody pushed.

8.3 · gitleaks job (added)

gitleaks:
  steps:
    - actions/checkout@v5  with: { fetch-depth: 0 }   # full history
    - gitleaks/gitleaks-action@v2

Scans the diff and history for anything shaped like a credential and fails the build. This is the guardrail against re-introducing the keys that were previously committed.

8.4 · hadolint job (added)

hadolint:
  strategy:
    matrix: { dockerfile: [ ./-yatrubackend-/Dockerfile, ./-yatruSathiFrontend-/Dockerfile, ./-Yatrusathi-AIchatbot/Dockerfile ] }
  steps:
    - hadolint/hadolint-action@v3.1.0
      with: { dockerfile: ${{ matrix.dockerfile }}, ignore: DL3008,DL3013,DL3018, failure-threshold: warning }

A matrix runs the job once per Dockerfile in parallel. hadolint is a Dockerfile best-practice linter; the ignore list drops rules that don't apply to these base images.

Net supply-chain posture. Every push: dependency CVE report (Trivy fs), image CVE gate (Trivy image), secret scan (gitleaks), Dockerfile lint (hadolint), deep static analysis (CodeQL), and known-vuln npm report (npm audit). Weekly: Dependabot PRs across five ecosystems + a scheduled CodeQL re-scan.

9 · Application changes that make the code deployable

Four small, guarded source changes — behaviour is unchanged unless you opt in with an environment variable.

9.1 · Backend — Postgres support  -yatrubackend-/backend/settings.py

DATABASE_URL = os.getenv("DATABASE_URL", "").strip()
if DATABASE_URL:
    import dj_database_url
    DATABASES = { "default": dj_database_url.parse(
        DATABASE_URL, conn_max_age=int(os.getenv("DB_CONN_MAX_AGE", "600")),
        conn_health_checks=True, ssl_require=env_bool("DB_SSL_REQUIRE", False)) }
else:
    DATABASES = { "default": { "ENGINE": "django.db.backends.sqlite3",
        "NAME": os.getenv("SQLITE_PATH", str(BASE_DIR / "db.sqlite3")),
        "OPTIONS": { "timeout": 20 } } }
Why this was needed. The app stored everything in SQLite — a file on local disk. In the cloud, containers are disposable; when one restarts its disk is wiped and all data is lost. This lets a DATABASE_URL point at a managed PostgreSQL service. Local dev, tests and CI are unchanged — with no DATABASE_URL it still uses SQLite exactly as before.
  • conn_max_age=600 — reuse a DB connection for 10 minutes.
  • conn_health_checks=True — verify a pooled connection is alive before reuse.
  • ssl_require — force TLS to the database in the cloud.

requirements/base.txt gains dj-database-url==2.3.0 and psycopg[binary]==3.2.13 (the driver).

Two recurring Terraform patterns

  • for_each = toset([...]) — the same block produces one resource per list item (e.g. two namespaces, two secrets, three ECR repos).
  • IRSA ("IAM Roles for Service Accounts") — a specific pod assumes a specific AWS role with no stored key. Used by all three controllers and available to the app pods.

Example — eks.tf access entries (the security-critical bit)

access_entries = merge(
  { github_ci = {                              # the CI deploy role
      principal_arn = module.github_deploy_role.arn
      policy_associations = { edit = {
        policy_arn = "…/AmazonEKSEditPolicy"
        access_scope = { type = "namespace",
                         namespaces = [var.app_namespace, "${var.app_namespace}-staging"] }
  } } } },
  { for arn in var.cluster_admin_principals : "admin_${md5(arn)}" => {  # you
      principal_arn = arn
      policy_associations = { admin = {
        policy_arn = "…/AmazonEKSClusterAdminPolicy", access_scope = { type = "cluster" } } } } }
)

The CI identity can edit workloads in the two app namespaces and nothing else — it cannot create namespaces, touch kube-system, or read other secrets.

11.4 · backend.yaml — Deployment + Service + HPA

kind: Deployment  (replicas: 2)
  initContainers:
    - name: migrate         # runs to completion BEFORE the app container
      image: backend
      command: ["python","manage.py","migrate","--no-input"]
      env: SECRET_KEY←DJANGO_SECRET_KEY, DATABASE_URL   (from the Secret)
  containers:
    - name: backend  image: backend  port 8000
      envFrom: [configMapRef: yatrusathi-config]
      env: SECRET_KEY, DATABASE_URL, RESEND_API_KEY, ADMIN_PASSWORD   (from the Secret)
      readinessProbe: GET /api/  (X-Forwarded-Proto: https)   # no traffic until this passes
      livenessProbe:  GET /api/                                # restart if this starts failing
      resources: requests {cpu 100m, mem 256Mi}  limits {cpu 1, mem 512Mi}
---
kind: Service  (name backend, port 8000)          # stable internal name, load-balances across pods
---
kind: HorizontalPodAutoscaler  (backend, 2→6 replicas, target 70% CPU)
ObjectRole
DeploymentKeeps N identical pods running; rolling-replaces them on a new image.
initContainer migrateDB migrations run to completion before any app container starts.
readinessProbe / livenessProbeGate traffic until ready; restart if unhealthy.
X-Forwarded-Proto: https headerMimics the load balancer so Django's HTTPS redirect doesn't loop the health check.
requests / limits"requests" is reserved by the scheduler; "limits" is the hard cap (CPU throttled, memory over-limit = killed).
ServiceA stable virtual IP + DNS name that spreads traffic across the pods despite churn.
HPAAdds/removes pods to hold average CPU near target. Needs metrics-server.
Known trade-off. migrate as an initContainer runs on every pod start. Migrations are idempotent so it's safe, but two pods starting together could race. For zero-downtime, promote it to a single pre-deploy Job. Documented, not yet changed.

12.2 · .github/scripts/deploy-eks.sh

set -euo pipefail
: "${AWS_REGION:?}" "${EKS_CLUSTER_NAME:?}" "${OVERLAY:?}" "${NAMESPACE:?}" "${ENV_NAME:?}" "${SHA:?}"

ACCOUNT_ID="$(aws sts get-caller-identity --query Account --output text)"
REGISTRY="${ACCOUNT_ID}.dkr.ecr.${AWS_REGION}.amazonaws.com"
aws eks update-kubeconfig --name "$EKS_CLUSTER_NAME" --region "$AWS_REGION"

frontend_tag="$SHA"
if [[ -n "${APP_HOST:-}" ]]; then                 # rebuild the frontend for THIS env's URLs
  frontend_tag="${SHA}-${ENV_NAME}"
  aws ecr get-login-password … | docker login … "$REGISTRY"
  docker build ./-yatruSathiFrontend- \
    --build-arg "VITE_API_BASE_URL=https://${APP_HOST}/api/" \
    --build-arg "VITE_CHATBOT_URL=https://${APP_HOST}" \
    --build-arg "VITE_SENTRY_DSN=${VITE_SENTRY_DSN:-}" \
    --build-arg "VITE_SENTRY_ENVIRONMENT=${ENV_NAME}" \
    --build-arg "VITE_SUPABASE_URL=${VITE_SUPABASE_URL:-}" \
    --build-arg "VITE_SUPABASE_ANON_KEY=${VITE_SUPABASE_ANON_KEY:-}" \
    -t "${REGISTRY}/yatru-sathi-frontend:${frontend_tag}"
  docker push "${REGISTRY}/yatru-sathi-frontend:${frontend_tag}"
else
  echo "::warning::APP_HOST not set for ${ENV_NAME} — frontend will call localhost."
fi

pushd "$OVERLAY" >/dev/null
kustomize edit set image \
  "backend=${REGISTRY}/yatru-sathi-backend:${SHA}" \
  "frontend=${REGISTRY}/yatru-sathi-frontend:${frontend_tag}" \
  "chatbot=${REGISTRY}/yatru-sathi-chatbot:${SHA}"
popd >/dev/null

kubectl apply -k "$OVERLAY"
for d in backend frontend chatbot; do
  kubectl -n "$NAMESPACE" rollout status "deployment/${d}" --timeout=180s
done
LineWhat & why
: "${VAR:?}"Abort with a clear message if a required variable is missing.
aws eks update-kubeconfigWrite a kubeconfig so kubectl can reach the cluster.
the APP_HOST blockVite bakes URLs in at build time, so the frontend image is environment-specific: rebuild it with this env's public host, tag <sha>-staging / -production. Backend/chatbot images are host-agnostic (built once by push-ecr).
kustomize edit set image …Rewrite the manifests to reference the images just pushed.
kubectl apply -kSend the rendered manifests to the cluster.
kubectl rollout status … --timeout=180sWait for every Deployment to report its new pods healthy; fail the job otherwise — this is what turns a bad deploy into a red pipeline.
Why a script, not inline YAML. Both deploy jobs run the identical sequence — one place to fix a bug, and the logic can be read and tested on its own.
